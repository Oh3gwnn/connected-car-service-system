# 가상 CCU(통신 모듈) 설계 및 수동 검증 가이드

이 문서는 모바일 앱(Swagger UI)에서 보낸 원격 제어 명령을 차량 내부에서 처음으로 수신하는 가상 CCU(Connectivity Control Unit) 모듈의 개발 배경과 수동 검증 시나리오를 정의합니다.

---

### 1. 이 파일을 만드는 이유 (Why)

실제 커넥티드 카(Connected Car) 내부에서 제어 명령은 다음과 같은 흐름으로 흐릅니다:

사용자가 스마트폰 앱에서 "시동/공조 켜기"를 누릅니다.

클라우드 서버(FastAPI)가 무선망을 통해 차량의 CCU(통신 모듈)로 MQTT 메시지를 쏩니다.

CCU는 이 무선 신호를 받아서 차량 내부 네트워크인 CAN 버스(vcan0) 메시지로 변환하여 다른 제어기(ECU)들에게 뿌려줍니다.

즉, simulator/ccu.py는 차량의 '무선 통신 안테나이자 내부 Gateway' 역할을 모사하기 위해 반드시 필요합니다. 이 관문이 열려야 서버의 신호가 차량 내부 하드웨어(CAN) 영역으로 들어올 수 있습니다.

---

### 2. 우리가 얻고자 하는 결과 (Desired Result)

우리가 이 단계에서 눈으로 확인해야 할 최종 수동 검증의 형태는 다음과 같습니다.

동작 흐름: Swagger UI(HTTP POST) ➡️ FastAPI 서버 ➡️ MQTT Broker ➡️ CCU 시뮬레이터 (수신 완료 로그 출력)

성공 로그 예시 (CCU 터미널 화면):

> [CCU 수신] 새로운 무선 명령이 도착했습니다!  
> └─ 차대번호(VIN): KMHCT41BPJU123456  
> └─ 제어 명령: START_CLIMATE  
> └─ 설정 온도: 23.5°C  
> ⚡ [CAN 변환] CAN 버스로 제어 메시지 송신을 시도합니다... (ID: 0x123, Payload: [0x01, 0xEB, ...])

---

### 3. SDET/QA 관점에서 알아야 할 핵심 포인트 (Must-Know)

**① 와일드카드 구독(Wildcard Subscription)의 중요성**

우리는 토픽을 ccs/vehicle/+/control 형태로 구독합니다. 중간의 +는 단일 레벨 와일드카드로, 어떤 차대번호(VIN)를 가진 차량이든 자신의 명령 통로를 동적으로 구독할 수 있게 해줍니다.

실무에서 차대번호마다 하드코딩해서 구독하도록 짜면, 테스트 차량이 바뀔 때마다 코드를 수정해야 하는 결함이 생깁니다. 이를 방지하기 위한 유연한 설계 방식입니다.

**② 차량 레벨에서의 데이터 정합성 검증 (Edge Validation)**

아무리 백엔드(FastAPI)에서 정상적인 데이터를 보냈더라도, 통신 구간에서 데이터가 유실되거나 깨질 수 있습니다.

가상 CCU는 수신된 JSON 페이로드가 유효한 형태인지 2차 검증을 수행하고, 깨진 데이터(예: 온도 누락, 잘못된 명령어 바이트)일 경우 차량 내 다른 제어기(ECU)로 CAN 메시지를 쏘지 않고 무시하도록 설계되어야 안전합니다.
